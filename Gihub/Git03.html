Чуть подробнее о Git

Что такое «система контроля версий» и почему это важно?

Система контроля версий— это система, записывающая изменения в файл или набор файлов в течение времени и позволяющая вернуться позже к определённой версии.
Многие предпочитают использовать систему контроля версий для копирования файлов в другую директорию (возможно, в директорию с меткой времени, если они достаточно сообразительны). Этот подход очень распространён, потому что он очень прост, но он также невероятно подвержен ошибкам. Легко забыть, в какой директории вы находитесь, и случайно записать данные не в тот файл или скопировать файлы, которые вы не хотели копировать.
Для решения этой проблемы программисты давно разработали локальные системы контроля версий, которые имели простую базу данных, хранившую все изменения файлов под контролем версий.

RCS - локальная система управления версиями была впервые разработана Уолтером Ф. Тичи в Университете Пердью в начале 1980-х годов. RCS размещается на одном компьютере, управляет множеством версий файлов. RCS автоматизирует хранение, извлечение, регистрацию, идентификацию и слияние версий. RCS полезна для часто редактируемых текстов, включая исходный код, программы, документацию, графику, статьи и типовые письма. Хотя в настоящее время RCS в основном вытеснена Git и другими громоздкими системами контроля версий, она все еще может использоваться в качестве легковесной системы для периодического управления небольшим количеством файлов.

Git - распределённая система управления версиями. Проект был создан Линусом Торвальдсом для управления разработкой ядра Linux, первая версия выпущена 7 апреля 2005 года; координатор — Дзюн Хамано.

VCS - (Version Control System ) - система контроля версий. VCS позволяет вернуть файлы к состоянию, в котором они были до изменений, вернуть проект к исходному состоянию, увидеть изменения, увидеть, кто последний менял что-то и вызвал проблему, кто поставил задачу и когда и многое другое. Использование VCS также значит в целом, что, если вы сломали что-то или потеряли файлы, вы спокойно можете всё исправить. В дополнение ко всему вы получите всё это без каких-либо дополнительных усилий.

Необходимость сотрудничества с разработчиками, работающими в других системах, привела к созданию сетевых решений. Так , например, для решения этой проблемы были разработаны централизованные системы контроля версий (ЦККС). Эти системы (такие как CVS, Subversion и Perforce) имеют единый сервер, на котором хранятся все версионированные файлы, и ряд клиентов, которые извлекают файлы из этого центрального хранилища. В течение многих лет это было стандартом для контроля версий. Однако у такой конфигурации есть и серьёзные недостатки. Это единая точка отказа, и единое хранилище данных.
Здесь на помощь приходят распределенные системы контроля версий (DVCS). В DVCS (таких как Git, Mercurial или Darcs) клиенты не просто загружают последний снимок файлов; вместо этого они полностью зеркалируют репозиторий, включая всю его историю.

Краткая история Git

Как и многие великие дела в жизни, Git начался с некоторого созидательного разрушения и ожесточенных споров.
Ядро Linux — это проект с открытым исходным кодом, имеющий довольно большой масштаб. В первые годы поддержки ядра Linux (1991–2002) изменения в программном обеспечении распространялись в виде патчей и архивных файлов. В 2002 году проект ядра Linux начал использовать собственную распределенную систему контроля версий (DVCS) под названием BitKeeper.
В 2005 году отношения между сообществом, разработавшим ядро ​​Linux, и коммерческой компанией, создавшей BitKeeper, разорвались, и бесплатный статус инструмента был отменен. Это побудило сообщество разработчиков Linux (и в частности Линуса Торвальдса, создателя Linux) разработать собственный инструмент.
С момента своего появления в 2005 году Git развивался и совершенствовался, став простым в использовании, но при этом сохранив свои первоначальные качества. Он невероятно быстр, очень эффективен при работе с крупными проектами и обладает потрясающей системой ветвления для нелинейной разработки.

Организация системы хpанения информации в Git.

Главное отличие Git от любой другой системы контроля версий заключается в способе работы с данными. Концептуально большинство других систем хранят информацию в виде списка изменений в файлах. Эти системы рассматривают хранимую ими информацию как набор файлов и изменения, внесенные в каждый файл с течением времени. Вместо этого Git рассматривает свои данные скорее как серию снимков миниатюрной файловой системы. Каждый раз, когда вы фиксируете изменения или сохраняете состояние проекта, Git, по сути, делает снимок того, как выглядят все ваши файлы в данный момент, и сохраняет ссылку на этот снимок. Для повышения эффективности, если файлы не изменились, Git не сохраняет файл снова, а только ссылку на предыдущий идентичный файл, который он уже сохранил. Git рассматривает свои данные скорее как поток снимков. Это важное отличие Git от почти всех других систем контроля версий.
Кроме того, в Git все данные проверяются на контрольную сумму перед сохранением, и затем к ним обращаются по этой контрольной сумме. Эта функциональность заложена в Git на самых низких уровнях и является неотъемлемой частью его философии. Вы не можете потерять информацию при передаче или получить повреждение файла без того, чтобы Git не смог это обнаружить. Механизм, используемый Git для вычисления контрольной суммы, называется хешем SHA-1, состоящим из 40 16-ричных чисел. Фактически, Git хранит все в своей базе данных не по имени файла, а по хешу его содержимого.
При выполнении действий в Git почти все они лишь добавляют данные в базу данных Git. Система с трудом позволяет отменить какие-либо действия или удалить данные.

В Git есть три основных состояния, в которых могут находиться ваши файлы: изменено , подготовлено и зафиксировано .
- «Изменено» означает, что вы внесли изменения в файл, но еще не зафиксировали их в базе данных.
- «Подготовлено» означает, что вы отметили измененный файл в его текущей версии для включения в следующий снимок коммита.
- «Зафиксировано» означает, что данные надежно сохранены в вашей локальной базе данных.
